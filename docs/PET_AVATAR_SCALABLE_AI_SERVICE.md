# Масштабируемый AI-сервис реконструкции питомца

**Статус:** согласованная целевая архитектура следующего этапа
**Дата:** 2026-08-01
**Цель:** локально разработать и отладить полный сервис реконструкции, после чего перенести тяжёлый AI-worker на отдельную машину с NVIDIA V100 без переделки Web UI, API и Unity-интеграции.

## 1. Главное решение

Система разделяется на обычный сервис приложения и специализированный GPU-worker.

- Web UI, API заданий, очередь, база и хранилище остаются на основной машине.
- AI-worker выполняет сегментацию, восстановление формы, построение текстур, риггинг и экспорт GLB.
- Сначала все компоненты запускаются на текущей машине для локальной отладки.
- Позже только AI-worker и веса моделей переносятся на машину с V100.
- Unity никогда не выполняет тяжёлую реконструкцию: она получает готовый ригованный GLB.

```text
Пользователь
    ↓
Web UI
    ↓
API заданий
    ↓
Очередь
    ↓
AI Reconstruction Worker
    ↓
GLB + текстуры + manifest + preview
    ↓
Хранилище результатов
    ↓
скачивание ZIP / загрузка в Unity
```

## 2. Это не LLM

Обычная языковая модель не является главным вычислителем этого pipeline. LLM можно использовать позже для диалогов питомца, характера, обработки текстового описания и оркестрации, но узнаваемую 3D-внешность создают специализированные vision/3D-модели.

Нужные классы моделей и алгоритмов:

1. Детекция и сегментация животного.
2. Сопоставление одного питомца на разных кадрах.
3. Оценка ракурсов, позы и анатомических ориентиров.
4. Multi-view fitting общей параметрической модели собаки.
5. Уточнение морды, ушей, лап, хвоста и пропорций.
6. UV-проекция окраса и восстановление невидимых участков текстуры.
7. Оценка уверенности для достроенных областей.
8. Привязка к общему мобильному скелету.
9. Экспорт GLB 2.0 и контроль качества.

Для продукта предпочтительнее не генерировать произвольный mesh с нуля, а подгонять общую качественную модель собаки с известной топологией и скелетом. Это обеспечивает совместимость всех питомцев с одними анимациями Unity.

## 3. Из чего состоит AI-worker

AI-worker — не DLL и не обычный установочный файл. На первом этапе это отдельный контейнерный сервис, обычно на Python:

```text
PetAvatarReconstructionWorker/
├── api/
├── pipeline/
│   ├── segmentation/
│   ├── pose_estimation/
│   ├── reconstruction/
│   ├── texturing/
│   ├── rigging/
│   └── export/
├── providers/
├── models/
├── tests/
├── requirements.txt
└── Dockerfile
```

Состав среды:

- Python-код pipeline;
- PyTorch или другой inference runtime;
- CUDA-библиотеки;
- веса моделей (`.safetensors`, `.pth`, `.ckpt`, ONNX или TensorRT engine);
- HTTP/worker API;
- генератор GLB и диагностических метаданных.

Веса могут занимать много гигабайт и не должны храниться в Git. DLL или нативная библиотека возможны позже после стабилизации моделей, но для исследовательского этапа контейнер проще обновлять, проверять и переносить между GPU-машинами.

## 4. Локальная конфигурация первого этапа

Сначала все компоненты разворачиваются на текущей машине:

```text
Текущая машина
├── pet-avatar-web-api
├── pet-avatar-worker
├── очередь заданий
├── S3-совместимое хранилище
└── локальная база метаданных
```

Рекомендуемый локальный состав Docker Compose:

| Компонент | Назначение |
| --- | --- |
| `pet-avatar-api` | загрузка фотографий, статусы, выдача результатов |
| `pet-avatar-worker` | выполнение реконструкции |
| `redis` | очередь и краткоживущее состояние заданий |
| `minio` | локальное S3-совместимое хранилище фотографий и артефактов |

Текущая GTX 1060 используется для разработки интерфейсов, очереди, хранилища, отдельных лёгких моделей и низкокачественного inference. Тяжёлые этапы могут выполняться медленно, с уменьшенным разрешением, CPU offload или временно заменяться mock-provider.

Профили worker:

```text
mock       — инфраструктурная проверка без AI;
local-low  — облегчённый pipeline для GTX 1060;
gpu-v100   — рабочий inference на V100;
gpu-large  — профиль для GPU с большим объёмом VRAM.
```

## 5. Конфигурация после переноса на V100

После локальной отладки основная машина продолжает обслуживать пользователей, а GPU-worker переносится отдельно:

```text
Основная машина                    GPU-машина
├── Web UI                         └── AI Worker
├── API                                ├── CUDA runtime
├── очередь                            ├── веса моделей
├── база                               └── генерация GLB
└── объектное хранилище
```

Меняются только переменные окружения и профиль запуска worker. Контракты Web UI, API, задания, ZIP и Unity не меняются.

Следует заранее проверить конкретную V100: версии на 16 и 32 ГБ имеют разный запас памяти. Совместимость и допустимое качество нельзя гарантировать до выбора и измерения реального набора моделей.

## 6. Передача заданий и файлов

Нельзя передавать удалённому worker локальные пути вида `D:\uploads\dog.jpg`. Worker должен получать объектные URI или ограниченные по времени защищённые HTTP-ссылки.

Пример задания:

```json
{
  "jobId": "123",
  "profile": "local-low",
  "photos": [
    "s3://pet-avatar/uploads/123/front.jpg",
    "s3://pet-avatar/uploads/123/side.jpg"
  ],
  "output": "s3://pet-avatar/results/123/"
}
```

Пример результата:

```json
{
  "jobId": "123",
  "status": "ready",
  "model": "s3://pet-avatar/results/123/pet.glb",
  "preview": "s3://pet-avatar/results/123/preview.png",
  "manifest": "s3://pet-avatar/results/123/avatar.json",
  "confidence": 0.72
}
```

Worker обязан быть идемпотентным: повторная доставка одного `jobId` не должна создавать конфликтующие результаты. Нужны состояния `queued`, `running`, `ready`, `failed`, `cancelled`, прогресс по этапам, таймаут, повтор задания и диагностический код ошибки.

## 7. Выходной контракт для Unity

```text
pet-avatar.zip
├── pet.glb
├── textures/
│   ├── albedo.png
│   ├── normal.png
│   └── fur-mask.png
├── avatar.json
├── preview.png
└── README.md
```

`pet.glb` должен содержать mesh, UV, материалы, skin weights, общий skeleton и тестовую анимацию. `avatar.json` должен явно указывать provider, версии моделей, систему координат, единицы измерения, качество входных данных и confidence map.

## 8. Масштабирование

Масштабирование достигается добавлением worker-инстансов, а не копированием Web UI:

```text
API → очередь → worker V100 #1
             → worker V100 #2
             → worker GPU  #3
```

Каждый worker объявляет доступный профиль и объём ресурсов. Планировщик не должен выдавать тяжёлое задание worker, которому не хватает памяти. Ограничение параллельности задаётся отдельно для каждого GPU.

## 9. Сетевая безопасность и приватность

- Redis, MinIO и служебный API нельзя публиковать напрямую в интернет.
- Между основной и GPU-машиной используется частная сеть, VPN или защищённый туннель.
- Предпочтительно, чтобы worker сам устанавливал исходящие соединения и забирал задания.
- Доступ к объектам выдаётся по краткоживущим ссылкам или сервисным учётным данным с минимальными правами.
- Фотографии не включаются в итоговый ZIP.
- Срок хранения исходников и результатов должен быть конфигурируемым.
- Логи не должны содержать фотографии, токены или подписанные URL целиком.

## 10. Текущее состояние прототипа

Добавлена граница второй версии `bite-d-smal`: Web/API может выбрать внешний
лицензированный dog-specific adapter без изменения контракта задания и Unity-
артефакта. Runtime проверяет наличие UV, skin weights, текстурного материала,
анимации, общей топологии, skeleton ID и оценки geometry confidence до упаковки
результата.

Открытая версия BITE/D-SMAL разрешает только некоммерческие научные
исследования, а необходимые модели и данные выдаются после регистрации.
Поэтому код и веса не включаются в Git, а профиль по умолчанию не активирован.
Для локального некоммерческого обучения и тестирования разрешён явно выбранный
режим `research`; он не даёт права на production. Коммерческий запуск требует
отдельной лицензии и режима `commercial`. В обоих случаях нужен внешний adapter.
Наличие provider-контракта не считается доказательством узнаваемости.

В `PetCemeteryUnityApp/PetAvatarPrototype/` уже реализован и проверен интеграционный контур:

- Web UI загрузки фотографий;
- API заданий и прогресс;
- ZIP-контракт;
- rigged GLB;
- Unity loader/importer;
- процедурный provider `procedural-prototype`.

Процедурный provider является только `mock`-реализацией. Он создаёт техническую низкополигональную болванку, а не узнаваемую реконструкцию питомца. Его следует сохранить для быстрых интеграционных тестов, но не показывать как результат AI-реконструкции.

## 11. План реализации

### Этап 1. Разделение сервисов

- вынести provider в отдельный worker-процесс;
- определить версионированные схемы задания и результата;
- добавить очередь, объектное хранилище и состояния ошибок;
- сохранить текущий provider как профиль `mock`.

### Этап 2. Локальный AI pipeline

- подключить сегментацию и нормализацию фотографий;
- добавить оценку ракурсов и качества входа;
- выбрать параметрическую мастер-модель собаки;
- реализовать первый `local-low` fitting и проекцию окраса;
- показывать интерактивный 3D-preview вместо плоской картинки.

### Этап 3. Риггинг и Unity QA

- закрепить общий skeleton и topology contract;
- проверить базовые анимации и деформации;
- ввести мобильные бюджеты полигонов, текстур, памяти и FPS;
- автоматизировать headless-проверку GLB в Unity.

### Этап 4. Перенос на V100

- собрать CUDA-совместимый worker image;
- развернуть его на GPU-машине;
- подключить к защищённым очереди и хранилищу;
- измерить VRAM, время задания и допустимую параллельность;
- переключить production-профиль без изменения клиентских контрактов.

## 12. Критерии готовности следующего milestone

1. Одинаковое задание выполняется локальным и удалённым worker через один контракт.
2. Владелец узнаёт свою собаку на тестовом наборе без подписи.
3. Система явно отмечает приблизительно достроенные области.
4. Модель автоматически загружается в Unity и использует общий skeleton.
5. Повторные задания, ошибки и перезапуск worker не теряют состояние.
6. Веса и лицензии моделей разрешают предполагаемое использование.
7. Измерены время, VRAM и стоимость одной реконструкции на V100.
